enumeration.

## 2. Method

- `dml_probe.py` builds a CPU session and a DML session with the M4 session options:
  `ORT_ENABLE_ALL`, `ORT_SEQUENTIAL`, `enable_mem_pattern=false`, `enable_cpu_mem_arena=false`.
  A session whose provider list does not contain `DmlExecutionProvider` is reported as a DML
  failure, because ORT silently drops DML on an unusable device.
- Inputs are deterministic (seed 0): seeded uniform floats, random `uint8` images, sparse random
  binary masks for inputs named `mask`, zeros for integer/bool tensors. An all-zero feed would make
  several graphs produce trivial outputs and hide numerical differences.
- Dynamic input dimensions are overridden with `--shape` where the graph has a meaningful runtime
  shape (MI-GAN tiles, EfficientTAM memory bank). Otherwise unknown dimensions are set to 1.
- One or three warm-up runs precede timing; p50 is reported over 3–10 runs.
- Parity is `max(|cpu - dml|) / max(1e-6, max|cpu|)` over all outputs, plus max absolute difference.
- **Tracking throughput is a component-sum figure**, not a full pipeline run: Task 0 does not
  implement a tracker. Summing the measured per-component p50 is a conservative **upper bound** on
  throughput because it excludes host-side orchestration, memory-bank assembly, pre/post-processing
  and copies. Task 5 must re-measure the real pipeline (the brief says so explicitly).
- VRAM was sampled from the WDDM `GPU Process Memory` counters for the probe process (peak
  `Local Usage`, `Shared Usage`, `Dedicated Usage`) while SAM 2 vision encoder + memory attention +
  MI-GAN ran under DirectML. These counters include all GPU allocations of the process; on an iGPU
  the memory is shared system memory, not discrete VRAM.

### 3.1 End-to-end estimate (secondary, not a gate substitute)

Extrapolating the measured component costs to 300 frames (1080p30, 10 s), **one 512² inpainting tile
per frame**, no host overhead:

| Tracking + inpainting path | Estimated wall time | Plan target ≤ 10 min |
|---|---|---|
| SAM 2 CPU + MI-GAN CPU | 630.9 s (10.51 min) | misses by ~31 s |
| SAM 2 DML + MI-GAN DML | 1373.7 s (22.89 min) | **FAIL** |
| EfficientTAM CPU + MI-GAN CPU | 325.6 s (5.43 min) | passes |
| EfficientTAM DML + MI-GAN DML | 260.2 s (4.34 min) | passes |

This is optimistic: a large mask needs several tiles per frame, which multiplies the inpainting cost,
and the component-sum ignores host overhead. It shows that the per-component fps gates and the
end-to-end budget can disagree on this hardware; the Task 0 verdict below follows the explicit
per-component gates in the brief, not this extrapolation.

## 4. Per-model detail

### 4.1 SAM 2.1 Hiera-Tiny (fp32, 1024², 5-session video ONNX)

Source: `square-zero-labs/sam2.1-tiny-video-onnx`, revision
`3b2984dd865f6e9d2cc6aed0be6a5a5c2eb352ce`. The model card reports numerical validation against the
PyTorch `propagate_in_video_iterator` with worst per-frame mask IoU 0.9967.

| Graph | CPU p50 (ms) | DML p50 (ms) | Max rel. diff | Max abs. diff | DML placement |
|---|---:|---:|---:|---:|---|
| `vision_encoder.onnx` | 736.78 | 1665.77 | 8.54e-6 | 1.13e-5 | all 435 graph nodes fused into 1 DML node, no CPU fallback |
| `mask_decoder.onnx` | 53.42 | 59.77 | 5.15e-6 | 1.91e-6 | **373 DML + 112 CPU nodes** (fragmented) |
| `memory_attention.onnx` | 587.45 | 2309.34 | 1.73e-6 | 6.32e-6 | 21 DML nodes, no CPU nodes |
| `memory_encoder.onnx` | 39.86 | 91.29 | 2.47e-6 | 6.38e-6 | all 74 graph nodes fused into 1 DML node |
| `pointer_tpos.onnx` | 0.0091 | 0.0841 | 3.17e-7 | 1.07e-6 | 6 DML nodes |

`memory_attention` was measured with a realistic memory bank: `memory` and `memory_pos`
`[28736, 1, 64]`, object pointers `[4, 1, 64]`, current features `[4096, 1, 256]`. Changing the
memory-bank size from 1 token to 28736 tokens did not change the measured latency, so the graph's
dynamic memory dimension appears not to be the hot path on this export; this should be checked in
Task 5 with a real tracking loop.

**Verdict: `GO` for session creation and numerical parity; `NO_GO` for speed on the tested
hardware.** DML is 1.1–3.9× slower than CPU for these fp32 graphs on the iGPU. Tracking default stays
`sam2.1-hiera-tiny` per the brief's rule (it passed creation/parity), but Task 5 cannot enter
implementation until the speed gate is met on reference hardware.

### 4.2 EfficientTAM-Ti 512 (fp16, 5-session ONNX)

Source: `egordm/efficienttam-ti-512`, revision `ef8a773fc653fc46a2e87dd182cac0f8ef980cc1`.
`bundle.toml` declares `variant=fp16`, `image_size=512`, `num_maskmem=7`, `max_obj_ptrs=16`.

| Graph | CPU p50 (ms) | DML p50 (ms) | Max rel. diff | Max abs. diff | DML placement |
|---|---:|---:|---:|---:|---|
| `image_encoder.onnx` | 87.72 | 190.08 | 1.094e-2 | 7.81e-3 | all 898 nodes fused into 1 DML node |
| `prompt_encoder.onnx` | 1.565 | 1.348 | 8.296e-3 | 1.18e-2 | 94 DML + 27 CPU nodes |
| `mask_decoder.onnx` | 20.80 | 7.92 | **2.353e-2** | **4.69e-1** | all 588 nodes fused into 1 DML node |
| `memory_encoder.onnx` | 18.94 | 15.87 | 2.627e-3 | 8.06e-3 | all nodes fused into 1 DML node |
| `memory_attention.onnx` | 271.01 | 199.57 | 2.589e-3 | 7.81e-3 | **504 DML + 264 CPU nodes** (fragmented) |

The strict parity gate **fails on every component** (all > 1e-3). The worst is `mask_decoder`
(2.35e-2 relative, 0.469 absolute on fp16 logits). As a practical sanity check, thresholding the
`masks` output at 0 and computing IoU between the CPU and DML masks on one seeded synthetic prompt
gives **0.98896** (CPU 7,693 positive pixels, DML 7,618) — above the 0.98 target, but this is one
synthetic prompt, not the required 20 real frames.

**Shape contract finding.** With the default 1-token dynamic memory dimensions, the CPU session's
`memory_attention` run fails:
`Reshape node '/mem_attn/layers.0/cross_attn_image/Reshape_6': input shape {1,1,0,128,2},
requested {1,1,0,-1}`. Supplying realistic memory shapes (`spatial_memory` / `spatial_memory_pos`
`[7168,1,64]`, `obj_ptr` `[64,1,64]`) makes both CPU and DML run. Task 5 must pin these shapes and
treat the default dynamic graph as unusable.

**Verdict: `NO_GO`.** Sessions run, but numerical parity misses the stated threshold on every
component, `memory_attention` has a fragmented DML/CPU partition (264 CPU nodes), and the
component-sum speed is 2.4–2.5 fps against an 8 fps gate.

### 4.3 MI-GAN 512

Source: `andraniksargsyan/migan` (Picsart MIT `LICENSE`), revision
`406830d0fa60666da0071c342ad2fbc8f30c5c64`. Graph: `image [N,3,H,W] uint8`,
`mask [N,1,H,W] uint8`, output `result [N,3,H,W] uint8`.

| Input tile | CPU p50 (ms) | DML p50 (ms) | Max rel. diff | Max abs. diff |
|---|---:|---:|---:|---:|
| 512×512 | 685.32 | 452.67 | 3.92e-3 (= 1/255) | 1.0 (exactly 1 uint8 LSB) |
| 256×256 | 677.89 | 440.48 | 3.92e-3 | 1.0 |
| 128×128 | 675.62 | 437.26 | 3.92e-3 | 1.0 |

- DML session creation and 10 timed runs succeeded (`runs=10`, `warmup=3`).
- Node placement: **422 DML + 19 CPU** nodes; ORT forces shape/`Gather`/`Slice`/`Concat`/`Where`
  nodes to CPU. This is a warning, not a session failure.
- Output parity is at the quantisation floor: max 1 LSB on `uint8`, no pixel differs by more than 1.
- **The cost is independent of input tile size** (512², 256², 128² all ≈440 ms DML). The graph
  appears to process a fixed internal canvas, so cropping a small watermark does not make it cheaper.
- Throughput: **2.21 fps DML, 1.46 fps CPU**, against the ≥10 fps fast-path gate.
- CPU fallback: **usable** — 10 frames completed without error.

**Verdict: `NO_GO` for the fast-path fps gate on the tested hardware; `GO` for runtime
availability on both providers.** The 1-LSB output difference is acceptable for a `uint8` image
pipeline; the blocker is speed.

### 4.4 LaMa 512

Source: `g-ronimo/lama`, revision `386a67cedf9b8bb4fe76798c10c8d77abc0a5cc8`. Three variants were
evaluated because the recommended fixed-512 fp16 graph could not be created on DML.

| Variant | CPU p50 (ms) | DML result | Max rel. diff |
|---|---:|---|---|
| `lama_512_fp16.onnx` (preferred, full fp16 compute, fixed 512²) | 611.91 | **Session creation failed** | n/a |
| `lama_fp16.onnx` (weight-only fp16, 512² input via override) | 1994.73 | Session created, **first run failed** | n/a |
| `lama_512_int8.onnx` (int8 weights, fixed 512²) | 537.18 | **Session creation failed** | n/a |

Failure details:

- `lama_512_fp16` / `lama_512_int8`:
  `ONNXRuntimeError : 6 : RUNTIME_EXCEPTION : Exception during initialization:
  MLOperatorAuthorImpl.cpp(2851) ... Exception(1) ... 80070057 参数错误 (E_INVALIDARG)`.
- `lama_fp16`: session created, but the first run failed at `Reshape` node `node_view`:
  `Exception(5) ... 80070057 参数错误 (E_INVALIDARG)`.
- CPU throughput: 1.63 fps (preferred variant), 1.86 fps (int8), 0.50 fps (weight-only fp16),
  all below the ≥2 fps quality-path gate.

**Verdict: `NO_GO`.** The quality path cannot run on DirectML on this machine and does not reach
2 fps on CPU with the preferred graph. Task 6's quality path is blocked until a DML-compatible
LaMa export or an operator workaround is found and re-measured on reference hardware.

## 6. VRAM measurement

Workload: SAM 2 `vision_encoder` + `memory_attention` + `mask_decoder` + `memory_encoder` sessions
and MI-GAN session loaded together in one process, all on `DmlExecutionProvider` `device_id=0`,
running 1024²/28736-token/masked-512² workloads in a loop. Peak WDDM counters for the process:

| Counter | Peak |
|---|---:|
| `GPU Process Memory \ Local Usage` | **3597.8 MB** |
| `GPU Process Memory \ Shared Usage` | **3494.1 MB** |
| `GPU Process Memory \ Dedicated Usage` | 103.7 MB |
| `GPU Process Memory \ Total Committed` | 3597.8 MB |

The ≤4 GB target is met on this measurement (≈3.6 GB), but this is an **iGPU with shared system
memory**, not a 6 GB discrete card. The value includes all DML session weights and activations for
both models loaded concurrently; the production design may load them sequentially and use less.
Treat the 4 GB/6 GB-card gate as **not fully validated** until it is repeated on a discrete GPU with
`QueryVideoMemoryInfo`.

## 8. GO / NO_GO conclusion

```text
TECHNICAL_GATE: NO_GO (tested hardware: AMD Radeon(TM) Graphics iGPU, 2 CU-class, shared memory)

sam2.1-hiera-tiny     session_create=PASS  parity=PASS  speed=FAIL  -> NO_GO (speed)
efficienttam-ti-512   session_create=PASS  parity=FAIL  speed=FAIL  -> NO_GO
migan-512             runtime=PASS (DML+CPU)  speed=FAIL (2.21 fps)   -> NO_GO (fps gate)
lama-512              DML=FAIL (0x80070057)  CPU=1.63 fps            -> NO_GO
cpu-fallback          migan=usable                                  -> PASS
vram                  3597.8 MB peak (iGPU shared)                  -> PASS (caveat)
nvidia-qa             not measured (no NVIDIA GPU present)          -> BLOCKED
```

**Why NO_GO.** On the only available machine, every performance gate misses: SAM 2 tracking
0.24 fps DML / 0.71 fps CPU (gate ≥5), EfficientTAM 2.41 fps DML / 2.50 fps CPU (gate ≥8), MI-GAN
2.21 fps DML / 1.46 fps CPU (gate ≥10), LaMa 1.63 fps CPU and DML session creation fails (gate ≥2).
EfficientTAM also fails the numerical parity gate on every component. The required NVIDIA QA row
cannot be measured without NVIDIA hardware. The technical gate is therefore not satisfied, and
Task 5/6 must not enter implementation on this evidence.

**What would change it.**
1. Re-run this probe on a discrete reference AMD GPU (RDNA3/RDNA4, ≥8 GB) and on an NVIDIA QA
   machine, using the same scripts and thresholds. If the discrete card meets the per-component fps
   gates, the verdict can move to GO for that hardware profile.
2. Investigate EfficientTAM fp16 parity: compare fp32 exports, check whether DML fp16 math order is
   the cause, and validate thresholded mask IoU on 20 real frames. The strict ≤1e-3 gate is not met.
3. Repair the LaMa DirectML path: try an opset/operator-compatible export (the failing
   initialization is `E_INVALIDARG` in `MLOperatorAuthorImpl`), or accept CPU-only LaMa if the
   quality path can meet its fps gate there.
4. Investigate MI-GAN's fixed internal canvas: the graph costs ~440 ms regardless of input tile, so
   cropping does not help on this build. Check whether a different dynamic-resolution export or a
   smaller model removes the fixed cost.
5. Measure real end-to-end latency and quality on the M4 corpus before re-scoping any threshold. The
   optimistic end-to-end estimates in §3.1 are not a substitute for the per-component gates.

Because licensing is also unresolved (`TECHNICAL_EVALUATION_ONLY`, no legal sign-off), release is
blocked regardless of the technical result.
